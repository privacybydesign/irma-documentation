## What this document is

This Protection Profile (PP) applies to the WSCA-BE (the Wallet Secure Cryptographic Application running on Wallet Provider backend infrastructure) as a standalone Target of Evaluation (TOE) for Common Criteria evaluation under the EUCC scheme established by Commission Implementing Regulation (EU) 2024/482 ([Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)). A certificate of conformity issued against this PP may serve as an assurance input for national wallet certification schemes pursuant to Article 4 of Commission Implementing Regulation (EU) 2024/2981 ([Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)). The PP is developed based on Regulation (EU) No 910/2014 as amended by Regulation (EU) 2024/1183 (eIDAS 2.0) and Commission Implementing Regulation (EU) 2024/2981 ([Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)). It defines the security problem (assets, threats, OSPs, assumptions), security objectives, security functional requirements and security assurance requirements for this TOE ([§3–§7, p. 21–50](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=21)).

## Scope and object of certification

- TOE definition: the TOE is the WSCA deployed in the wallet provider's back-end infrastructure ("WSCA-BE (TOE)"); it operates as an authenticated remote signing service that verifies the user's identity and authorisation, validates the wallet instance key binding, and instructs the WSCD-HSM to generate signing keys and to sign data submitted by the Wallet Instance ([§1.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=7)).
- TOE type: an application (WSCA) on a dedicated hardened backend server; Article 2(4) of CIR (EU) 2024/2981 defines the WSCA as "an application that manages critical assets by being linked to and using the cryptographic and non-cryptographic functions provided by the WSCD" ([Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)); ([§1.2.5, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=10)).
- The TOE manages the full lifecycle of Attested key pairs (and optionally WIA device-binding key pairs), but the attested private keys never leave the security context of the WSCD-HSM; all cryptographic operations are handled by the WSCD-HSM ([§1.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=7)).
- TOE boundary: the WSCA-BE does NOT include the WSCD-HSM hardware or firmware, the Wallet Instance application or device, the log server, the Internet-facing gateway or load balancer, or any wallet provider backend services other than the WSCA-BE module itself ([§1.2.6, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12)).
- Required non-TOE hardware/software: WSCD-HSM (following CEN EN PP 419 221-5 or an equivalent PP); Hardened Server (hardened against remote side-channel and microarchitectural attacks); Gateway Server (at least DDoS protection, intrusion detection, antivirus and firewall); Database (external storage of TOE assets); Log Server (environment ensures log data is not deleted); Wallet Provider Backend; Wallet Instance (certified according to (EU) 2024/2981); Reliable Time Source ([§1.2.5.1, p. 10–11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=10)).
- "Remote HSM architecture" (what is where): the WSCA executes on Wallet Provider backend infrastructure (WSCA-BE), the WSCD is implemented as a certified remote HSM that manages the critical private keys of the Wallet Unit (the attested keys for the KA and, if applicable, the WIA device-binding key pair), and the Wallet Instance additionally holds a device-resident key in hardware-backed storage (e.g. a Secure Element or platform-provided hardware-backed keystore) that serves as the possession-based authentication factor for remote authentication to the WSCA/WSCD ([Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)).
- The WSCA-BE runs on a dedicated hardened server that runs no other services, positioned behind gateway servers that manage and filter all external communications to the Wallet Provider backend and the Wallet Instance; the WSCA is expected to use an external database to store the Authentication Reference Data (ARD); every security-relevant action is an audit log entry, cryptographically tied to wallet units and transactions, transmitted to an external log server ([§1.2.5, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=10)).
- The WSCA-BE, hardened server, WSCD, Gateway server, external databases, log servers and their connections shall operate in a protected environment that limits physical access to the TOE to authorised privileged users ([§1.2.5, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=10)).
- TOE major security features: secure communication; Remote User Authentication (RUAP, ARD enrolment and management, transaction-bound UAE verification, PIN reset using a PUK, per-key authentication data held by the Wallet Instance); Wallet Provider authentication and role-based authorisation; cryptographic key management (delegating private-key protection and operations to the WSCD-HSM); WSCD-HSM access-control protection; attestation support (evidence binding attested public keys to WSCA/WSCD-generated keys for KA/WIA); protected cryptographic operations; multi-tenant isolation; security audit; self protection (self testing, secure initialisation, preserving a secure state) ([§1.2.6, p. 11–12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=11)).
- The TOE requires a secure and certified WSCD and a secured underlying server and secure operational environment as defined by the objectives in chapter 4 ([Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)).

## Who it applies to

- Scheme Owners, Evaluation Laboratories, CABs and EUDI Wallet providers are the primary audience; EUDI Wallet ecosystem stakeholders are the secondary audience ([cover table, p. 2](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=2)).
- ST author: must claim strict conformance when claiming this PP ([§2.4, p. 20](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=20)); must model key generation, distribution, derivation and cryptographic operations implemented by the TOE itself (WSCD-implemented mechanisms are out of scope of these SFRs and the WSCD ST shall be referenced) ([§6.3, App. Notes 4–7, p. 37–38](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=37)); must claim [FCS_RBG.1](/edi-stelsel-certification/requirements/nl-cs-wsca#fcs_rbg-1) (plus FCS_DRB.2 or FCS_DRB.3) if the server OS CSPRNG rather than the HSM DRBG is used ([§6.3.6, App. Note 8, p. 38](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=38)); is not expected to reproduce §1.3 in the ST ([§1.3, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12)). Security Targets shall provide evaluation evidence that the assumptions are satisfied in the specific deployment ([§3.5, p. 26](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=26)).
- Evaluator: ATE_IND.2 calls for evaluator-performed independent tests with emphasis on FCS_EXT_UAE evidence verification and FDP_ACF.1 multi-tenant access control; the AVA_VAN.5 notes state what the vulnerability analysis shall include, items (a)–(f) ([§7, Table 8, p. 50](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=50)).
- TOE developer: shall operate a vulnerability management process compliant with EN ISO/IEC 30111:2019 and Article 5 of (EU) 2024/2981 ([§3.4, OSP.VULN_MGMT, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=25)); ([§4.2, OE.VULNERABILITY_MANAGEMENT, p. 30](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=30)).
- Wallet Provider (S.WalletProvider): wallet provider backend application that communicates with the TOE through a mutually authenticated channel and requests operations ([§3.2, p. 23](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=23)); issues and signs WIA and KA after authenticating the attested public keys ([§1.3.2.3, p. 15](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=15)); shall ensure that TOE software updates are cryptographically signed, that the deployment pipeline verifies signatures before installation and that an SBOM is maintained for each deployed version ([§4.2, OE.SECURE_UPDATE, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=31)); shall protect the public part of AST.WSCA_WSCD_Signing_Key_Pair and the complete signing key chain used to issue the KA and WIA, verify the authenticity of attested public keys received from the WSCA-BE before including them in a KA or WIA, and require identity re-verification before reset or migration ([§4.2, OE.TRUSTED_WALLET_PROVIDER, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=31)); restricts admissible ARD ([§4.2, OE.RESISTANT_ARD, p. 30](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=30)); must revoke the Wallet Unit on User request, PID Provider request, or a security breach ([§1.3.6, p. 19](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=19)).
- Wallet Instance (S.WalletInstance): wallet application that requests operations on the TOE ([§3.2, p. 23](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=23)); is assumed to derive UAE cryptographically from a PIN-derived knowledge-based factor and a possession-based factor and to generate and use the required keys within the secure keystore, and the app is assumed to be from an official app store and/or authenticated in a secure way; the wallet shall only run on secure devices and shall be certified according to (EU) 2024/2981 ([§3.5, A.UAE_and_ARD, p. 26](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=26)); ([§4.2, OE.GENUINE_WALLET_INSTANCE, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=31)).
- Wallet User (S.WalletUser): end user who must be authenticated before any cryptographic action with their keys; does not manage or use keys directly; all communication is mediated by the S.WalletInstance; each S.WalletUser has exactly one S.WalletInstance ([§3.2, p. 23](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=23)); will not disclose authentication factors ([§4.2, OE.TRUSTED_WALLET_USER, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=31)).
- Administrators: assumed trusted and trained; the TOE is not expected to defend against a malicious Administrator ([§4.2, OE.TRUSTED_ADMIN, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=31)). The "technical administrator" is not a user role of the TOE; it maintains the operative environment including the underlying server ([§6.1.6, App. Note 1, p. 36](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=36)).
- WSCD-HSM: must be certified against EN 419 221-5 or an equivalent PP, protecting private keys at least per the "assigned key" definition ([§3.4, OSP.WSCD_CERT, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=25)); ([§4.2, OE.HSM_CERT, p. 30](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=30)).
- PID/Attestation Providers and Relying Parties: only indirectly connected to the TOE via the Wallet Instance; no assumptions on them are expected in this PP. For the Access Certificate Infrastructure / Trust Infrastructure, Table 15 states that keys in the WSCA/WSCD are not part of it and that no assumptions on it are expected in this PP ([Annex B.3, Table 15, p. 71](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=71)).

## Key points

- Conformance: CC:2022 Revision 1 including latest errata, Parts 1–5; "CC Part 2 extended and CC Part 3 Conformant" ([§2.1, p. 20](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=20)).
- Package claim: EAL 4 augmented with AVA_VAN.5, ALC_DVS.2 and ALC_FLR.3 ([§2.2, p. 20](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=20)); ([§7, p. 49](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=49)).
- The PP claims no conformance to other PPs and requires strict conformance of any ST or PP that claims conformance to it ([§2.3–§2.4, p. 20](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=20)).
- All threats assume HIGH attack potential against the WSCA-BE, "consistent with EAL4 augmented with AVA_VAN.5 and the requirements of (EU) 2024/2981" ([§3.3, p. 24](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=24)).
- Rationale for the assurance level: EAL4+ is required because the product "is intended to withstand sophisticated attacks"; ALC_DVS.2 replaces ALC_DVS.1; ALC_FLR.3 has no dependencies; AVA_VAN.5 because the TOE "shall be highly resistant to any kind of penetration attacks" ([§8.4, p. 65](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=65)).
- RUAP: every PIN verification is a live and fresh interaction between the Wallet Instance and the WSCA; the Wallet Instance demonstrates UAE derived from a knowledge-based factor (derived from the PIN) and a possession-based factor; UAE is verified against ARD shared during enrolment ([Terminology, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=4)). RUAP shall meet Level of Assurance High of CIR (EU) 2015/1502 (at least two factors from different categories; resistance to guessing, eavesdropping, replay and manipulation with high attack potential) ([§1.3.2.2, p. 14](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=14)).
- WSCA/WSCD-level user authentication is required at a minimum for: initial generation of KAs and WIA; user approval of selective disclosure to a Relying Party; deleting a PID/attestation and attested keys; requesting issuance of a new PID or Attestation ([§1.3.2.2, p. 14](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=14)).
- Before invoking any WSCD-HSM operation the WSCA-BE shall verify UAE that is (a) bound to the user's registered ARD, (b) bound to the transaction context, (c) within its validity window, (d) not previously used, with (e) resilience against tampering or PIN (or PUK) brute force; requests lacking valid evidence are rejected and logged ([§4.1, OT.USER_AUTH, p. 28](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=28)).
- [FIA_UAE_EXT.1](/edi-stelsel-certification/requirements/nl-cs-wsca#fia_uae_ext-1) as instantiated: challenge of at least 128 bits of entropy from an RBG meeting [FCS_RBG.1](/edi-stelsel-certification/requirements/nl-cs-wsca#fcs_rbg-1); transaction context includes challenge, user identity, requested operation and wallet user identifier, associated with the session; evidence must show both the possession-based and the PIN-derived knowledge-based factor were verified; validity period is an ST assignment ([§6.5.11, p. 43](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=43)). [FIA_UAE_EXT.2](/edi-stelsel-certification/requirements/nl-cs-wsca#fia_uae_ext-2) requires a nonce registry and denial of evidence referring to unissued, already-used or expired challenges ([§6.5.12, p. 43](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=43)).
- After a defined number of unsuccessful wallet-user authentication attempts the TSF shall lock the wallet user and notify the wallet user via an out-of-band notification channel (applies to attempts for the same Wallet Instance) ([§6.5.1, p. 40](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=40)).
- Private keys of wallet users are generated within and never exported from the WSCD-HSM; the WSCA-BE holds only opaque key handles and stores only a minimum of private/symmetric keys (session keys and secure channel authentication data) ([§4.1, OT.KEY_PROTECT, p. 28](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=28)).
- The WSCA-BE shall use the WSCA/WSCD signing key only for signing the public key of key pairs generated within the WSCD-HSM "and bind it to the wallet user" ([§4.1, OT.KEY_ISOLATION, p. 28](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=28)).
- Per-key authorisation data is generated by the WSCD-HSM at key generation, sent to the wallet instance and provided with each operation; it is a TOE asset to be protected during use and securely deleted when no longer needed ([§4.1, OT.KEY_ISOLATION, p. 28](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=28)); ([§3.1, AST.WSCD_HSM_Access_Credentials, p. 23](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=23)).
- If ARD is stored in an external database, the TOE shall first verify its authenticity and integrity and shall not rely solely on the database ([§3.1, AST.Authentication_Reference_Data, p. 21](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=21)). ARD shall be constructed so that the knowledge-based factor cannot be verified without a secret held by the WSCA-BE or the WSCD ([§4.2, OE.RESISTANT_ARD, p. 30](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=30)).
- Mutually authenticated secure channels are required between the TOE and the Wallet Instance, the WSCD and the Wallet Provider; each transaction identifier is bound to AST.Wallet_Instance_Authentication_Data ([§4.1, OT.WSCA_SECURE_CHANNEL / OT.WSCD_SECURE_CHANNEL / OT.WALLET_PROVIDER_SECURE_CHANNEL, p. 29](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=29)).
- The channel to the WSCD-HSM shall identify the HSM via its hardware attestation certificate, protect against replay of HSM commands, detect modification of HSM responses, and the TSF shall refuse HSM responses that fail integrity verification ([§6.8.1, App. Note 13, p. 46](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=46)).
- Audit: a cryptographically protected, tamper-evident record for each security-relevant event (wallet user identifier, HSM key handle, relying party identifier where applicable, UAE reference, outcome and potential threats); evidence of origin and receipt verifiable by the Wallet Provider; Wallet Provider actions logged ([§4.1, OT.AUDIT, p. 29](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=29)). The TSF shall reject remote API requests from Wallet Instances when local audit storage is full ([§6.1.4, FAU_STG_EXT.1.5, p. 36](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=36)).
- The WSCA-BE shall refuse to start if its binary or configuration has been modified since the last integrity baseline; WSCD-HSM Access Credentials shall not be stored in plaintext ([§4.1, OT.SELF_PROT, p. 29](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=29)); on initialisation errors the TOE is halted ([§6.7.6, FPT_INI.1.3, p. 46](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=46)).
- Credential management and HSM operations are transactional: complete fully (including HSM confirmation and audit record) or roll back with an audit record of the failure ([§6.7.4, App. Note 12, p. 45](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=45)).
- Keys and key material, including per-key authorisation data, are destroyed when no longer needed and on revocation, deprovisioning, factory reset or authorised deletion ([§6.3.4, FCS_CKM.6.1, p. 37](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=37)); ([§3.4, OSP.SECURE_ERASURE, p. 26](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=26)).
- Management functions: for the Wallet Provider — TOE self-identification of version and configuration, TOE maintenance, audit data review, Factory Reset, deletion or reset of user authentication data; for the Wallet User — modifying user authentication data, PIN reset using PUK, Wallet Instance Migration ([§6.6.2, p. 44](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=44)). Roles maintained: Wallet User, Wallet Instance, Wallet Provider ([§6.6.1, p. 43](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=43)).
- Cryptography: only algorithms mandated by applicable implementing acts or approved under the ECCG Agreed Cryptographic Mechanisms (ACM); a mechanism not yet in ACM requires a security assessment and documented justification and shall be replaced or updated when an applicable ECCG mechanism becomes available ([§3.4, OSP.CRYPTO_STANDARDS, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=25)).
- The WIA technical validity period shall be less than 24 hours ([§1.3.2.3.2, p. 15](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=15)) (informative section ([§1.3, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12))).

## Process

The document describes the Wallet Unit lifecycle in §1.3, which it labels "of informative nature"; the ST author is not expected to reproduce it ([§1.3, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12)).
1. Installation — Wallet Instance distributed preferably through an official OS distribution channel; otherwise the Wallet Provider provides an authenticity/integrity check mechanism ([§1.3.1, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12)). The Wallet Instance establishes secure channels with the Wallet Provider and the WSCA/WSCD ([§1.3.1.1, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12)) and sends initial technical and security-posture data to the Wallet Provider ([§1.3.1.2, p. 12–13](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=12)).
2. Activation (Wallet Provider, User, Wallet Instance) — creation of a Wallet Provider user account associated with the Wallet Instance; registration of two user authentication mechanisms (OS-level user authentication and WSCA/WSCD-level RUAP); initial generation and issuance of WIA and KA ([§1.3.2, p. 13–14](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=13)).
3. KA/WIA generation (User via Wallet Instance, WSCA/WSCD, Wallet Provider) — after WSCA/WSCD-level user authentication the WSCA/WSCD generates attested keys; attested public keys (and the WIA public key) are signed by WSCA/D_PRIV_KEY so that the Wallet Provider can authenticate them; the Wallet Provider signs the KA with WP_SIG_PRIV1 and the WIA with WP_SIG_PRIV2 ([§1.3.2.3, p. 15–16](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=15)).
4. Issuance (PID/Attestation Provider, Wallet Instance, WSCA/WSCD) — the Wallet Instance authenticates the Provider via Access and Registration Certificates; the Provider verifies WIA and KA signatures, validity and revocation status and requests proof-of-possession via nonce signing; for a device-bound credential the Provider binds it to one of the public keys in the KA; the credential is sent via the OpenID4VCI Credential Response ([§1.3.3, p. 16–17](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=16)).
5. Disclosure (Wallet Instance, User, Relying Party, WSCA/WSCD) — the Wallet Instance authenticates the RP, authenticates the user, obtains explicit approval and signs the transaction-bound presentation through the WSCD/WSCA; the RP verifies it ([§1.3.4, p. 18–19](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WSCA-RC1.1_-_for_publ.pdf#page=18)).
