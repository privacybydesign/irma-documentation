## What this document is

The document lists the requirements, following a risk analysis, that a mobile device, referred to as the User Device, must fulfil to provide an adequately secure operating environment for an EUDI Wallet Instance ([§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5)). It exists because the security of the Wallet Instance cannot be established solely through evaluation of the wallet application; it also depends on the security capabilities, configuration and lifecycle support of every mobile device on which the Wallet Instance is permitted to run ([§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5)). Collectively, the controls are intended to protect the Wallet Instance against attackers with high attack potential, including attackers capable of remote exploitation or physical access to the device ([§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5)).

## Scope and object of certification

- Object of the conditions: the User Device (UD), the mobile device on which an EUDI Wallet Instance operates and which forms the foundational security layer of the Wallet Unit ([§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5)).
- Architecture context: critical cryptographic operations and long-term key material may be protected by remotely operated Wallet Secure Cryptographic Applications and Devices, but the Wallet Instance still relies on its mobile device to protect locally processed authentication factors, personal data, attestations, transaction information and security-relevant application data ([§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5)).
- Topics covered: vulnerability management, protection against exploitation, trusted firmware, secure generation of random values, secure cryptographic implementations, hardware-backed isolation of cryptographic keys, application sandboxing, integrity attestation, device access control, protection of stored data, secure networking and preservation of user privacy ([§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5)).
- The word "Conditions" appears in the title and document type; the body uses "requirements" and "security controls", each control having a "Requirements" and an "Evaluation criteria" subsection ([cover, p. 1](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=1); [Document control, p. 2](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=2); [§1, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=5); [§2, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)).

## Who it applies to

- User Device (UD): the subject of every "Requirements" clause ("The UD shall …") ([§2.1–2.12, p. 6–11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)).
- Wallet Instance (WI): the WI shall obtain integrity attestations for the app and possibly OS at runtime ([§2.8.2, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10)); [SC-04](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-04) criteria address RNGs used under control of the WI or whose outputs are accessible to the WI ([§2.4.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=7)); known-answer testing covers primitives provided by the UD and used by the WI ([§2.5.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8)). Other runtime checks (e.g. OS version / security patch level, secure lock screen) are stated without naming an actor ([§2.1.2, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6); [§2.9.2, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11)).
- The wallet's design / Wallet Provider Backend: the wallet's design shall be capable of revoking WIs when the associated UD can no longer ensure its security, for example by associating the WI with device information in the Wallet Provider Backend ([§2.1.2, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)).
- Trusted environment ("never in the UD itself"): validates key attestations and integrity attestations ([§2.6.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8); [§2.8.2, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10)).
- Opposite connection end of the WI: shall perform server-side checks that the correct protocols are used in a standard-compliant way ([§2.11.2, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11)).
- Audiences named in the Document control table: Scheme Owners, Evaluation Laboratories, CABs, EUDI Wallet providers, and EUDI Wallet ecosystem stakeholders ([Document control, p. 2](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=2)). The document does not state which actor performs the "due diligence" criteria.

## Key points

- [SC-01](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-01): the UD shall receive regular, timely security updates addressing disclosed vulnerabilities in its first- and third-party components ([§2.1.1, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)); the OS version / security patch level shall be checked at runtime, and the wallet's design shall be capable of revoking WIs when the UD can no longer ensure its security (e.g. known exploits or significantly out of date) ([§2.1.2, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)).
- [SC-02](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-02): the UD shall follow best practices to protect against hardware and software vulnerabilities, like memory corruption attacks and supply chain attacks; evaluated by due diligence, e.g. review of platform documentation ([§2.2, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)).
- [SC-03](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-03): code executed with elevated privileges (bootloader, kernel, OS, TEE) shall be trusted and cannot be rolled back to a less secure version ([§2.3.1, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6)); where secure boot is not always enforced, its activation status shall be checked at runtime; unpatchable exploits, e.g. in the boot-up sequence, may make this control unenforceable ([§2.3.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=7)).
- [SC-04](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-04): the UD shall implement an RNG providing unpredictable randomness to generate cryptographic keys and nonces, with each output of the RNG being only accessible to a single app ([§2.4.1, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=7)). Evaluation criteria: (1) for RNGs under control of the WI, where available, UD APIs shall be used to determine that the security strength is sufficient (e.g. at least 128 bits); (2) where no strength information is available at runtime but outputs are accessible to the WI, runtime health tests shall be performed; (3) where runtime checks are not available, where possible, primitives and protocols that do not rely on strong randomness shall be used (e.g. nonce-reuse resistant block cipher modes, deterministic signature schemes); (4) where runtime checks and deterministic schemes are not possible, due diligence shall be done, e.g. via platform documentation and available security certifications ([§2.4.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=7)).
- [SC-05](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-05): the UD shall provide standard-compliant and vulnerability-free implementations of cryptographic primitives not implemented by the wallet app; known-answer testing shall be performed for all UD primitives used by the WI ([§2.5, p. 7–8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=7)).
- [SC-06](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-06): the UD shall provide an isolated environment for keys with key generation, storage, deletion/zeroization and use; no export; key attestations; and purposeful design against physical and logical tamper and side-channel attacks ([§2.6.1, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8)).
- [SC-06](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-06): the environment shall be a dedicated SE or a hardware-backed TEE; for TEEs three additional requirements apply: only trusted code with secure boot, strongly isolated memory, and retention of security properties if the rich OS is compromised ([§2.6.1, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8)).
- [SC-06](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-06) evaluation: runtime checks that critical key material is in an SE or TEE; key attestations obtained at runtime and validated in a trusted environment, never in the UD itself; if considered necessary for additional assurance, due diligence via an off-device analysis of whether the SE/TEE meets the security level required by the considered attacker model ([§2.6.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8)).
- [SC-06](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-06) assurance guidance: a valid certificate traceable to the UD (named examples: EUCC, FIPS 140-3, SESIP, GlobalPlatform) ([§2.6.2, p. 8–9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8)); for SEs, a composite certificate covering the hardware platform and a concrete application is ideal, and for the highest assurance the hardware itself should have a valid EUCC certificate against PP0084 or PP0117 ([§2.6.2, p. 9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=9)); without a certificate, assurance can be obtained e.g. via independent functional and penetration testing and other publicly available information ([§2.6.2, p. 9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=9)); for TEEs, ten properties (a–j), "among others", may be used as additional indicators, such as hardware isolation, small auditable code base, vendor support and vulnerability history ([§2.6.2, p. 9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=9)).
- The document notes that the required non-exportability of keys is usually not covered by certifications of the hardware platform but is rather a property of composite certifications ([§2.6.2, p. 9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=9)), and that "independent security certifications provide assurance in the fulfilment of security requirements, but do not necessarily result in a more secure product overall" ([§2.6.2, p. 9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=9)).
- [SC-07](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-07): the UD shall be able to or provide means to isolate app processes, memory, cryptographic keys and data from unauthorized accesses by other apps or system services, including side channels, drawing on top of other running apps, abuse of accessibility services, and unwanted use by the UD itself (backups, personalization) ([§2.7.1, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10)); where applicable to the UD, runtime measures against other processes drawing on top of the wallet UI and against access to sensitive wallet data by other apps, plus due diligence on a non-bypassable app sandbox ([§2.7.2, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10)).
- [SC-08](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-08): the UD shall implement a hardware-supported attestation mechanism proving app integrity at runtime, and, where OS modifications are likely, provide support in obtaining OS integrity attestations; the WI shall obtain integrity attestations for the app and possibly OS at runtime, validated in a trusted environment ([§2.8, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10)).
- [SC-09](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-09): the UD shall implement a hardware-backed lock screen requiring authentication before granting full access to the device that is resistant to bypass; runtime checks shall enforce that it is activated ([§2.9, p. 10–11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10)).
- [SC-10](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-10): the UD shall protect app data stored at rest from extraction in plaintext by use of a secure memory encryption algorithm; on UDs whose OS does not always enforce memory encryption, its activation status shall be checked at runtime on every storage media where WI data is stored persistently; where information about the security strength of the algorithm (e.g. "use of at least XTS-AES with at least 128-bit keys") is not available at runtime, due diligence shall be done instead ([§2.10, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11)).
- [SC-11](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-11): the UD shall provide mechanisms preventing all unencrypted/plaintext networking and secure implementations of current network protocols (e.g. TLS 1.3) used for transactions, when not implemented by the wallet app itself; runtime checks plus server-side checks by the opposite connection end ([§2.11, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11)).
- [SC-12](/edi-stelsel/requirements/nl-cs-wi-conditions#sc-12): the UD shall not monitor apps or provide means to track app users in a way that discloses sensitive information about the wallet to the UD's vendor or third parties; evaluated by due diligence ([§2.12, p. 11–12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11)).
- Platform API examples are given for iOS (e.g. UIDevice.current.systemVersion, CryptoKit, App Attest, LocalAuthentication, Network.framework) and Android (e.g. android.os.Build.*, SecureRandom, KeyInfo, HIDE_OVERLAY_WINDOWS, filterTouchesWhenObscured, isAccessibilityDataSensitive, Play Integrity API, KeyguardManager, DevicePolicyManager, NetworkSecurityPolicy) as illustrations ("for example") ([§2.1.2, p. 6](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=6); [§2.4.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=7); [§2.6.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=8); [§2.7.2, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10); [§2.8.2, p. 10](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=10); [§2.9.2, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11); [§2.10.2, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11); [§2.11.2, p. 11](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-conditions-RC1.1_-_for_publ.pdf#page=11)).
