## What this document is

This Protection Profile (PP) defines the Wallet Instance (WI) as the Target of Evaluation, WI-(TOE), for the Remote HSM configuration of a European Digital Identity Wallet ([§Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=4)). It specifies the functional and assurance security requirements for the Wallet Instance within the FITCEM certification framework ([§Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=4)). It is intended to provide a common security baseline for evaluating the Wallet Instance as part of an EUDI Wallet using the Remote HSM architecture, including its security dependencies and interactions with the WSCA/WSCD ([§Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=4)). The PP is developed based on Regulation (EU) No 910/2014 as amended by Regulation (EU) 2024/1183 (eIDAS 2.0) and Commission Implementing Regulation (EU) 2024/2981 ([§Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=4)).

## Scope and object of certification

- TOE definition: the TOE is a European Digital Identity Wallet Instance, abbreviated WI-(TOE), "a mobile application designed to give users full control over how they manage and share their personal identity" ([§1.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=7)). It stores identification data and credentials from authorised PID/Attestation Providers, presents them to service providers online and in person, supports selective disclosure and offers a way to sign documents digitally ([§1.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=7)).
- TOE type: a mobile application installed on the User Device ([§1.2.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=8)).
- Exclusive configuration: "The TOE is designed exclusively for a remote HSM configuration, in which the security-critical cryptographic assets and operations are managed by a remotely deployed Wallet Secure Cryptographic Device (WSCD) accessed through the Wallet Secure Cryptographic Application (WSCA)." ([§1.2, p. 7](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=7))
- Remote HSM architecture (what is where):
  - The Wallet Instance operates on the user device and interacts with the WSCA running on Wallet Provider backend infrastructure, which in turn uses a certified remote HSM as the WSCD ([§Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=4)).
  - User Device (UD): hardware, operating system and software environment on which the Wallet Instance executes ([§1.2.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=8)).
  - WSCA: a WSCA implementation deployed on a hardened backend server; it provides security-critical cryptographic functionality, interfaces with the WSCD and ensures operations on critical assets are performed only after the required authorisation and User authentication ([§1.2.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=8)).
  - WSCD: a hardware security device used by the WSCA to protect critical cryptographic assets; it shall prevent unauthorised export or use of protected private keys ([§1.2.2, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=8)).
  - Keystore User Device (Keystore): a hardware-backed SE used for cryptographic assets not required to be protected by the WSCD; the possession factor used by the authentication protocol is managed in the keystore ([§1.2.2, p. 8-9](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=8)).
  - In the remote-HSM configuration "the critical private key is exclusively resident in the WSCA/WSCD" ([§A.2 Table 14, p. 51](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=51)).
- TOE boundary: the document has no section titled "TOE boundary". Figure 1 shows the Wallet Instance (TOE) as one box inside the User Device; the Key store is a separate box in the User Device; the WSCA and the WSCD-HSM are inside "Wallet Provider Infrastructure" within a "Secure Environment"; the "Wallet Unit" boundary encloses both the Secure Environment and the User Device; Wallet Provider Backend, User, PID / Attestation Providers and Relying Party are outside the Wallet Unit ([§1.2.1 Figure 1, p. 8](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=8)). The WSCA/WSCD, Wallet Provider, PID/Attestation Provider, Relying Party, QTSP/Remote QSCD and User are listed as "User and External Entities" that interact with the WI-(TOE) ([§2.4 Table 5, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=25)).
- Functions in scope of the lifecycle description: installation, activation (User account, User authentications, WIA/KA generation), PID/Attestation issuance, credential disclosure, pseudonyms, revocation/deletion, and additional functionality (QES and seal, Wallet-to-Wallet, migration, DPA reporting, Trust Mark, logging) ([§1.3, p. 12-20](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=12)).

Appendix B gives the developer a starting point for the functional design and for describing the actual TOE design; it "does not prescribe a specific software architecture" ([§B, p. 59](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=59)).
- Evaluation laboratory: may use both decompositions in Appendix B as "a traceable basis for verification and targeted testing", which "does not replace the detailed design evidence or evaluation activities required by the applicable methodology" ([§B, p. 59](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=59)). "The evaluation shall place greater focus on the assets and requirements covering T.USER_IMPERSONATION"; requirements mitigating T.LEAKED_PRESENTATION_DATA "shall also be evaluated, but with a more limited focus" ([§2.2, p. 23](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=23)).
- User (S.USER, OE.USER): operates the Wallet Instance and authorises security-sensitive operations; shall keep credentials and authentication factors confidential, protect the PIN including during entry, and use the Wallet Instance only under their own control ([§2.4 Table 5, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=25); [§2.5 Table 6, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=25)).
- Wallet Provider (S.WP, OE.WP, OE.APP_DISTRIBUTION): securely activate the Wallet Instance, issue and sign the WIA and KA, keep the signing key verifiable through the trusted-anchor chain, maintain validity/revocation status and revoke compromised Wallet Instances ([§2.5 Table 6, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=25)); support the Wallet Instance only on User Devices meeting OE.USER_DEVICE conditions ([§2.5 Table 6, p. 27](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=27)); distribute the Wallet Instance and updates via channels preserving authenticity and integrity, sign every release, release only certified versions, provide timely security updates and define a minimum supported version ([§2.5 Table 6, p. 27](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=27)). The Wallet Provider must revoke the Wallet Unit on User request, on PID Provider request, and on a security breach or compromise, and must regularly verify the security of the Wallet Unit ([§1.3.5, p. 19](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=19)).
- WSCA/WSCD (S.WSCA/WSCD, OE.WSCA/WSCD): protect security-critical keys, run an authenticated protected channel with the Wallet Instance, perform operations only after User authentication, keep a per-User failure counter the Wallet Instance cannot reset, block after consecutive failures with increasing delays, unblock only after a reset procedure (e.g. PUK), generate per-key authorisation data at key generation ([§2.5 Table 6, p. 25-26](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=25)).
- PID/Attestation Provider (S.PROVIDER, OE.PROVIDER): authenticate with access and registration certificates, verify WIA and KA (authenticity, validity, revocation), verify proof of possession for device-bound credentials, bind and sign issued credentials ([§2.5 Table 6, p. 26](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=26)).
- Relying Party (S.RP, OE.RP): authenticate with access and registration certificates, verify authenticity, integrity and freshness of each presentation, the Provider signature and proof of possession, and process only validly presented and authorised Personal Data ([§2.5 Table 6, p. 26](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=26)).
- QTSP / Remote QSCD (S.QTSP, OE.QTSP): protect qualified signing keys, sign only after User authentication and explicit authorisation, protect communication, return the result securely ([§2.4 Table 5, p. 25](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=25); [§2.5 Table 6, p. 27](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=27)).
- User Device (OE.USER_DEVICE): TEE or SE, hardware-backed keystore, key-usage restrictions, key and device attestation, trusted boot, sandboxing, OS-level User authentication, security updates for the supported period ([§2.5 Table 6, p. 27](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=27)).

## Key points

- Two User authentication mechanisms are enrolled: OS-level User authentication and the WSCA/WSCD-level Remote User Authentication Protocol (RUAP) ([§1.3.2.2, p. 13](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=13)).
- OS-level authentication ([FSR_LOCAL_AUTH](/edi-stelsel-certification/requirements/nl-cs-wi#fsr_local_auth)) shall be multi-factor (device possession plus a knowledge- or inherence-based factor), enforced at startup and before security-sensitive actions, and expire after the applicable inactivity timeout ([§3.1 Table 10, p. 32](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=32)).
- RUAP ([FSR_REMOTE_AUTH](/edi-stelsel-certification/requirements/nl-cs-wi#fsr_remote_auth)) shall meet Level of Assurance High of CIR (EU) 2015/1502, use at least two factors from different categories, and resist guessing, eavesdropping, replay and manipulation "with high attack potential" ([§3.1 Table 10, p. 32](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=32)).
- The User Authentication Evidence (UAE) is derived from a knowledge-based factor (derived from the PIN) and a possession-based factor; it is verified against the Authentication Reference Data (ARD) ([§Background, p. 4](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=4)); the ARD is derived and shared with the WSCA/WSCD during initial enrolment, and each PIN verification is performed through a "live and fresh interaction" ([§3.1 Table 10, p. 32](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=32)). Disclosure of the ARD "shall not by itself enable User impersonation" ([§2.1 Table 1, p. 21](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=21)).
- A PUK can be integrated in the protocol to reset the knowledge-based factor ([§3.1 Table 10, p. 32](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=32)).
- Per-key authentication data is sent to the WI-(TOE) at key generation and provided at every security-sensitive cryptographic operation of that key ([§3.1 Table 10, p. 33](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=33)).
- WSCA/WSCD-level authentication is required at least for initial generation of KAs and WIA, User approval of selective disclosure, deleting a PID or attestation, and requesting issuance of a new PID or Attestation ([§1.3.2.2, p. 14](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=14)).
- The WIA technical validity period "shall be less than 24 hours", measured from the Wallet Provider's integrity verification to the expiry time in the WIA; the TOE must prove its integrity to the Wallet Provider before a WIA is generated ([§3.1 Table 10, p. 33](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=33)).
- The KA is signed with WP_SIG_PRIV1 and the WIA with WP_SIG_PRIV2 ([§1.3.2.3.1, p. 14](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=14); [§1.3.2.3.2, p. 15](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=15)). The TOE shall present a KA only to authorised PID/Attestation Providers during issuance and "shall not present a KA to a Relying Party" ([§3.1 Table 10, p. 34](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=34)). The TOE sends a KA only for device-bound PIDs/Attestations ([§1.3.3.2, p. 17](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=17)).
- The WIA device-binding key pair may be managed by the WSCA/WSCD or by the Wallet Instance ([§1.3.2.3.2, p. 15](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=15)).
- If RP_ACC_CERT or RP_REG_CERT validation fails, the TOE shall not disclose the requested PID or attestation ([§3.1 Table 10, p. 35](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=35)).
- The TOE shall not delegate security-sensitive User approval and disclosure decisions "to a browser, operating-system component or other intermediary application" ([§3.1 Table 10, p. 36](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=36)).
- Supported formats: SD-JWT VC for remote presentation and ISO/IEC 18013-5 mdoc for proximity presentation ([§1.3.3.3, p. 17](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=17)). Protocol flows: OpenID4VCI, OpenID4VP, ISO/IEC 18013-5, ISO/IEC 18013-7 and Digital Credentials API ([§3.1 Table 10, p. 34](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=34)).
- Migration Object shall not contain WIA, KA, attribute identifiers/values or private keys of PIDs and device-bound attestations; the PID is re-issued before other attestations ([§3.1 Table 10, p. 39](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=39)).
- Transaction logs shall not contain actual attribute values unless legislation requires it; Wallet Provider access to logs only with explicit prior User consent ([§3.1 Table 10, p. 40](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=40)).
- The User-initiated factory reset shall delete the PIDs and electronic attestations, transaction logs and Wallet Instance configuration and settings, and request secure deletion of associated cryptographic assets from the WSCA/WSCD and applicable secure keystores ([§3.1 Table 10, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=31)).
- When rooting/jailbreaking, unauthorized developer or debug mode, execution in an emulator or app-virtualization environment, or other conditions invalidating the TOE's security assumptions are detected, the TOE shall terminate or disable all security-critical functionality and not perform security-critical operations until an acceptable security state has been restored ([RSR_OPER_MOD](/edi-stelsel-certification/requirements/nl-cs-wi#rsr_oper_mod)) ([§3.2 Table 11, p. 43](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=43)).
- The PIN shall not be persistently stored or logged; PIN-derived data shall be cleared immediately after use ([RSR_PIN_ENTRY](/edi-stelsel-certification/requirements/nl-cs-wi#rsr_pin_entry)) ([§3.2 Table 11, p. 42](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=42)).
- Cryptography shall follow the ECCG Agreed Cryptographic Mechanisms; mechanisms not yet included shall be explicitly identified, justified and subject to approval by the certification/evaluation process ([RSR_CRPTO](/edi-stelsel-certification/requirements/nl-cs-wi#rsr_crpto)) ([§3.2 Table 11, p. 45](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=45)).
- RNG: the WI-(TOE) must use a hardware RNG via SE or TEE, or a DRBG compliant to NIST SP 800-90A or ISO/IEC 18031 seeded by at least two entropy sources (one external trusted source, one from the mobile device); reseeding at least when the integrity/confidentiality of its state cannot be assured and at least every 24 hours of continuous operation ([RSR_RNG](/edi-stelsel-certification/requirements/nl-cs-wi#rsr_rng)) ([§3.2 Table 11, p. 45](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=45)).
- OE.USER_DEVICE: the Wallet Provider shall support the Wallet Instance only on User Devices that provide, among others, a TEE or SE, a hardware-backed keystore, a trusted boot mechanism, application sandboxing and security updates for the period during which the Wallet Provider supports the device ([§2.5 Table 6, p. 27](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=27)). [RSR_USERDEVICE](/edi-stelsel-certification/requirements/nl-cs-wi#rsr_userdevice): "The TOE shall check that the User Device and OS shall at minimum" provide, among others, a TEE or SE, a trusted boot mechanism, application isolation/sandboxing and mechanisms for secure and timely security updates ([§3.2 Table 11, p. 41-42](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=41)).
- The WI-(TOE) shall be installed through an official application distribution channel (e.g. Google Play Store or Apple App Store) or a mechanism with equivalent authenticity and integrity protection ([§3.1 Table 10, p. 31](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=31)).
- Assurance: the cover states assurance level "High/High" for identity proofing (CIR 2015/1502) and evaluation (EU Regulation 2019/881) ([§Document metadata, p. 2](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=2)). FITCEM is EN 17640:2022, which "defines the fixed-time cybersecurity evaluation methodology applicable to the evaluation of the Wallet Instance TOE" ([§Background, p. 5](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=5)). ## Process

The document describes the Wallet Unit lifecycle (not a certification process) ([§1.3, p. 12-20](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=12)):
1. Installation: Wallet Instance distributed preferably via an official OS distribution channel; otherwise the Wallet Provider provides an authenticity/integrity check mechanism (Wallet Provider) ([§1.3.1, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=12)).
2. Mutual authentication channel: Wallet Instance establishes secure channels with the Wallet Provider and the WSCA/WSCD (WI-(TOE)) ([§1.3.1.1, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=12)).
3. Initial data: WI-(TOE) sends technical data, system diagnostics and security-posture signals to the Wallet Provider; the Wallet Provider minimises collection (WI-(TOE), Wallet Provider) ([§1.3.1.2, p. 12](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=12)).
4. Activation – Wallet Provider User account: User registers; Wallet Provider associates the account with the Wallet Instance (User, Wallet Provider) ([§1.3.2.1, p. 13](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=13)).
5. Activation – User authentications: User enrols OS-level authentication and RUAP; knowledge and possession factors bound to the ARD, ARD shared with WSCA/WSCD (User, WI-(TOE), WSCA/WSCD) ([§1.3.2.2, p. 13-14](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=13)).
6. Activation – WIA and KA: User performs WSCA/WSCD-level authentication; WSCA/WSCD generates attested keys; Wallet Provider issues and signs KA and WIA (User, WSCA/WSCD, Wallet Provider) ([§1.3.2.3, p. 14-15](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=14)).
7. Issuance – Provider authentication: TOE verifies the Provider's ISS_ACC_CERT and, where applicable, ISS_REG_CERT (WI-(TOE)) ([§1.3.3.1, p. 16](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=16)).
8. Issuance – Wallet Unit authentication: TOE sends WIA and KA(s); Provider verifies signatures, validity, revocation status and proof of possession via nonce (WI-(TOE), WSCA/WSCD, Provider) ([§1.3.3.2, p. 16-17](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=16)).
9. Issuance – generation: for a device-bound PID or Attestation, the Provider binds the credential to one of the public keys in the applicable KA, signs with ISS_SIG_PRIV and returns it via OpenID4VCI Credential Response (Provider) ([§1.3.3.3, p. 17](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=17)).
10. Disclosure: TOE authenticates the RP (RP_ACC_CERT, RP_REG_CERT), authenticates the User, shows RP identity, requested attributes, intended use and evaluation outcome, obtains approval, and signs a transaction-bound presentation via the WSCD/WSCA; RP verifies the presentation (WI-(TOE), User, WSCA/WSCD, RP) ([§1.3.4.1-1.3.4.2, p. 18](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=18)).
11. Revocation/deletion: Wallet Provider revokes the Wallet Instance (revoked status at all index positions in its WIAs) and, where the compromise affects a WSCA/WSCD, the WSCA/WSCD (a WSCD is revoked at all index positions in the corresponding KAs); for a revocable PID, the PID Provider must revoke the PID if either has been revoked; the Wallet Unit shall support secure deletion of its contents through a factory reset (Wallet Provider, PID Provider) ([§1.3.5, p. 19](pathname:///files/edi-stelsel/2026-11-06/NL-CS-WI-RC1.1_-_for_publ.pdf#page=19)).
